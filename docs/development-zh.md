# Scenes Skill Creator 开发历程

> 对应版本：`@cloudplugin/dsh-skill-creator` 0.0.3
> 文档语言：简体中文

## 1. 目的与范围

本文按阶段记录插件从「面板能打开但点不动」到 0.0.3 发布的实际过程：每个阶段做了什么、为什么这么做、踩了哪些坑。

几点约定：

- 文中出现的数字均为当次**实测输出**，未做平滑修饰，包括不好看的那部分。
- 「弯路清单」如实保留，不为了好看而删。
- 每条故障尽量写成「现象 → 原因 → 修法」，便于后来者对照排查。

## 2. 阶段 0：基座修复

起点是一个能打开、但点了没反应的面板。按现象归因：

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 面板 404 | 路由没有挂到服务上 | 在 `inject` 里声明所需服务 |
| `agent id undefined` | 创建 agent 时没带会话标识 | 补 `sessionId` |
| run 空转 | 发给会话的消息缺 `role:'user'` | 补上 `role` |
| 只有一个工具可用 | 工具集没有挂载 | 在 `setup` 里挂 preset |
| 卡在审批不往下走 | 权限预设不足 | 调整权限预设 |

修完之后第一次真跑：**121 步 / 10.9 分钟**，`validate-skill.sh` 结果为 **PASS 32 / FAIL 0 / WARN 2**。这一次真跑证明了「插件驱动的会话能跑完官方 creator 的流程」，后续所有工作都建立在这个基座上。

## 3. 阶段 1：真跑流程

改造前，插件只负责给出提示词，用户要自己复制到别处粘贴执行——插件本质上是「提示词生成器」。

改造后，官方 creator 被放进**真实会话**里执行，面板实时回显步骤。这一步之后，阶段、工具步、心跳这些显示才有意义，也才有了后面「看数据做优化」的可能。

## 4. 阶段 2：三分类与表单

- 接入第三个分类（华为云）。
- 华为云原有的 5 个字段并成 1 个「功能概括」大文本域，减少填写负担。
- 三类各自使用**结构化占位符**，不再共用一套。

## 5. 阶段 3：评测机制

这一阶段建立评分与修复闭环：

- **10 分制**评分 + 修复循环 + 扣分明细 + 报告。
- 后续补了一个缺陷修复：字段改名遗漏（`severity` → `level`）。该 bug 的后果是**评测 agent 没有结论时白送 3 分**——属于「沉默即通过」的错误，方向性比数值错误更危险。
- 增加**无提升早停**，避免在明显收敛不了的修复轮上继续烧时间。
- 通过后界面只显示「**通过**」，不再显示轮次，减少无关噪声。
- **阶段 3 修订（评分口径照搬导致的常数化）**：平台那个分数是「相对数据库基线 + 外部门禁」，本地面板两者都没有，照搬公式的后果是首轮成本(1)+效率(2) 恒为满分、`passScore 8.5` 形同虚设（三次真实运行都是 10.00/10，修复闭环一次都没触发）。修订为：
  1. 成本/效率**始终**适用绝对上限（`evalTokenBudget`/`evalDurationCapSeconds`/`evalMaxToolCalls`/`evalMaxLlmCalls`/cli·sdk·api 上限，工具失败与重试绝对为 0），有基线时再叠加「≤ 基线×1.1」，更省不罚；
  2. 「功能可用」改用**外部证据**：必须真实执行被测 skill 自带夹具（huawei/api `templates/test-vars.json`、generic `evals/evals.json`）≥ `minFixtureCases` 条并逐条给出命令+观测+对比结论，评测 agent 自编用例不再构成达标依据；
  3. 加回一组**本地确定性门禁**（SKILL.md/frontmatter、夹具存在且可解析、结构校验 error=0、华为云 creator 的 `validate-skill.sh` 无 FAIL），任一不过 → 总分上限 `gateScoreCap`(7.0) 且 `verdict !== 'pass'`，扣分明细/修复提示词/报告里都列出。

## 6. 阶段 4：无人值守与健壮性

按实际故障逐条修，这一阶段的每个改动都对应一次真实踩坑：

| 故障 | 处理 |
| --- | --- |
| creator 发问导致卡死 | 禁止向用户提问 + 若仍发出 `ask_user_question` 则自动代答（禁止变更类操作、按只读继续） |
| 20 分钟硬顶误杀长跑任务 | 改为「活动续期的静默看门狗 + 120 分钟绝对兜底」 |
| 机器休眠 2h33m 被误判为死 | 识别系统休眠，重新计时、不判死 |
| 「目标目录未确定，跳过评测」 | 增加产物目录自动发现 |
| 步骤日志截断路径导致抓错 skill | 由 `resolveSkillDir` 从 creator 写过的真实路径反推含 `SKILL.md` 的最近目录 |
| 用户觉得「卡住」 | 补时间感：心跳显示「已用时 X 分钟 · 最后活动 Y 秒前」 |

## 7. 阶段 5：记录持久化

这是本项目最严重的一类问题——**数据丢失**。

退出时 `disposeAll()` 里先 `runs.clear()` 再 `flush()`，于是**每次退出都写入一个空文件**。代码本身没有语法错误、测试也未必覆盖，但用户看到的是记录一次次消失。

修法（按重要性）：

1. **原子写**，避免写到一半留下半截文件。
2. **`.bak` 备份**与 **`.bak` 回退**。
3. **逐条容错**：单条记录损坏不影响其余记录加载。
4. **无条件并集**：合并已有内容，而不是直接覆盖。
5. **先存后清**，颠倒原来的顺序。
6. **终态立即落盘**。
7. `scripts/recover-runs.mjs` 支持从**会话日志重建**记录；已成功重建 **18 条**历史记录。
8. 列表限 **5 行滚动**，避免长列表拖垮面板。

## 8. 阶段 6：提效（先测再改）

优化之前先测。两个样本的实测数据：

| 样本 | 步数 | 耗时 | 步 / 分钟 |
| --- | --- | --- | --- |
| `file-list` | 74 | 14 分 | 5.3 |
| `git-list` | 197 | 52 分 | 3.8 |

时间去向分布：

| 类别 | 占比 |
| --- | --- |
| 执行命令 | 31–42% |
| 改文件 | 16–34% |
| 环境侦察 | 仅 1–3% |

最后一行**推翻了原本的猜想**：原以为环境侦察是大头，实测只有 1–3%。据此新增 `EFFICIENCY_DIRECTIVES`，方向是：**批量工具调用 / 整批验证 / 一次改到位 / 不重复读改**。

这一阶段的价值不在改动本身，而在于「先读真实运行数据，再决定优化什么」这个顺序。

## 9. 阶段 7：发布

第一步是**读 DSH 随包代码搞清规则**，而不是猜。确认到的事实：

- 没有插件市场。
- bundle 的判定条件是 `dsh.bundle` 非 null。
- peer 依赖只检查 `@deepseek-ai/dsh*`。
- client 走 `exports["./client"]`，且**模块 id 必须等于包名**。
- `files` 白名单会挡住未导出的 `exports`，因此 `"./locale/*.json"` 是**必需**的导出项。

改名涉及**四处同步**，外加 profile 依赖键、锁文件与联接。

`files` 中排除了 `test/**`、`scripts/**`，以及会改动他人 profile 的 `dsh-install.mjs`。

补齐了 `LICENSE` / `locale` / `icon`。

npm 版本线：**0.0.1 → 0.0.2 → 包名一度改为 `@cloudplugin/scenes-skill-creator` 并发布 0.0.2 → 回退为 `@cloudplugin/dsh-skill-creator`（自 0.0.3 起）**。

仓库侧：GitHub 仓库 + `dsh-plugin` topic；向 awesome-dsh-plugin 提交 **PR #7456**。

## 10. 弯路清单

如实记录，不做美化：

1. **补丁锚点过宽**，误吞了「技能名」那一行。
2. 用「start 之后第一个 `});`」做区间切割来重建测试文件，结果**切掉了 6 条测试**，而当时仓库没有 git，**无法恢复**。
3. 替换 `log()` 时漏掉收尾的 `};`，导致语法错误——靠 `node --check` 当场抓出。
4. 修改 profile 的 bundle 声明时，一个验证 run 正在跑 → 插件被卸载，该 run 被牵连中断（API 全部 404）。
5. 早停逻辑里插入了一行引用未定义变量的占位代码 → 评测流程整体 `failed`。
6. 占位符用了 `join('\n')` 的写法，结果写出了**字面量的反斜杠 n**。
7. 只看 `npm view` 就误判「发布失败」，实际是 packument 传播延迟，稍后即正常。
8. **编辑器类写文件工具产出的文件外部进程读不了（`EPERM`）**，并且有一次写入**静默丢失**。因此包括本文档在内的文档改为用 node / bash 写出，并对写出的文件做**异进程可读性验证**。

## 11. 最值钱的五条经验

1. **先读真实运行数据，再决定优化什么。** 阶段 6 的实测直接推翻了「环境侦察是大头」的猜想。
2. **用户看到的「卡住」，往往只是缺时间感。** 补一行心跳文案就消掉了大部分这类反馈。
3. **失败要能自证**：语法检查 + 全量测试 + 渲染断言。
4. **数据文件比代码更容易丢。** 原子写、`.bak`、先存后清、终态落盘不是可选项。
5. **把自己机器的默认值排除出发布物。**

## 12. 从上文教训直接导出的发布检查清单

清单每一项都能在上一节找到对应的真实事故，不是泛泛而谈：

- [ ] 写文件后做**异进程读回验证**（字符数 / 内容），并确认能被归档工具打进包；不用编辑器类写文件工具。
- [ ] 宣布完成前，拿出语法检查与全量测试的证据。
- [ ] 修改 profile / bundle 声明前，先确认**没有 run 在跑**。
- [ ] 补丁锚点必须唯一且足够具体，改完回查是否误吞相邻行。
- [ ] 切割 / 重建文件之前，先确认有版本控制可以回退。
- [ ] 持久化路径必须满足：原子写 + `.bak` + 逐条容错 + 先存后清 + 终态立即落盘。
- [ ] 发布结果不要只凭 `npm view` 单一信号判定。
- [ ] 发布物不得包含本机专用默认值与仅供内部使用的脚本。
